# ub-bit-API — 업비트 수수료 인지형 자동매매 엔진

업비트 Open API 기반 실매매 봇. 설계의 출발점은 신호가 아니라 **왕복 비용**이다.

수수료는 고정이고 예측 가능하다. 기대 수익은 고정이 아니며 예측이 빗나간다.
따라서 이 엔진은 "무엇을 살까"보다 **"이 비용을 넘길 수 있는 자리인가"**를 먼저 판정한다.
넘기지 못하면 매매하지 않는다.

---

## 비용 구조 (확정 팩트)

업비트 KRW 마켓 수수료는 매수 0.05%, 매도 0.05%다.

| 항목 | 값 |
|---|---|
| 수수료만 반영한 손익분기 | **0.1001%** |
| 슬리피지 5bp 포함 손익분기 | **0.2002%** |
| 순 1% 수익에 필요한 총상승률 | 1.202% |
| 일 10회전 시 확정 비용 드래그 | 일 1.98% / 20영업일 33.0% |
| 일 20회전 시 확정 비용 드래그 | 일 3.93% / 20영업일 55.1% |

마지막 두 줄이 이 프로젝트의 존재 이유다. **회전수는 전략 변수이자 확정 손실이다.**
알파가 0인 봇을 하루 20회전 돌리면 한 달 뒤 원금의 절반이 수수료로 사라진다.

```bash
python -m ubbit costs          # 이 표를 내 설정값으로 다시 계산
```

## 통계 검증 결과 — 엣지 입증 (2026-09-21)

백테스트 수익률은 증거가 아니다. 조합을 충분히 많이 돌리면 아무 전략에서나
흑자 구간이 나온다. 그래서 입증을 아래 **6개 관문 동시 통과**로 정의했다.

| 관문 | 기준 | 이유 |
|---|---|---|
| 표본 | OOS 거래 200건 이상, 종목 8개 이상 | 단일 종목 20건은 통계가 아니라 일화 |
| 구간 분리 | 워크포워드 OOS 구간만 집계 | 학습 구간 성과는 보고하지 않음 |
| 유의성 | 순열검정 p < 0.05/9 = 0.0056 | 가설 9개 → 본페로니 보정 |
| 견고성 | 부트스트랩 95% CI 하한 > 0 | 평균이 0과 구분되는가 |
| 분산 | 수익 종목 비율 55% 이상, 상위 5거래 이익비중 60% 이하 | 소수 종목·소수 거래 의존 배제 |
| 베타 | 노출시간 보정 단순보유 수익률 초과 | 시장 상승의 재포장인지 판별 |

`python -m ubbit validate --units 15 60 240 --modes breakout squeeze pullback`

KRW 마켓 상위 24종목(알트 포함) × 3 타임프레임 × 3 진입방식 = 9개 가설.

| 가설 | OOS 거래 | 거래당 순수익 | p-value | CI 하한 | 종목 breadth | 판정 |
|---|---|---|---|---|---|---|
| **breakout @ 240분** | **218건** | **+0.8486%** | **0.0035** | **+0.0056%** | **63%** | **✅ 입증** |
| breakout @ 60분 | 639건 | +0.3228% | 0.0010 | -0.0059% | 71% | ❌ CI 하한 |
| breakout @ 15분 | 384건 | -0.0910% | 0.4078 | -0.5142% | 45% | ❌ |
| pullback @ 60분 | 187건 | -0.4241% | 0.8101 | -1.0211% | 29% | ❌ |
| pullback @ 15분 | 111건 | -0.5786% | 0.9935 | -1.1114% | 24% | ❌ |
| pullback @ 240분 | 45건 | -0.3485% | 0.4623 | -2.2384% | 38% | ❌ |
| squeeze (전 구간) | 7~12건 | 표본 부족 | — | — | 17~29% | ❌ |

### 통계 검정은 통과했지만 — 아래 시뮬레이션이 이를 뒤집는다

breakout @ 240분봉

```
OOS 거래 218건 / 종목 19개
거래당 평균 순수익  +0.8486%   (중앙값 -1.8608%)
비용 전 평균       +1.0505%  → 수수료·슬리피지가 0.2019%p 잠식
승률 36.7%  손익비 1.40
부트스트랩 95% CI   [+0.0056%, +1.7688%]
순열검정 p-value    0.0035  (본페로니 보정 기준 0.0056)
수익 종목 비율      63%      상위 5거래 이익비중 15%
시장 노출 시간      3.9%
단순보유 벤치마크    종목당 -47.95%
```

**베타가 아니다.** 같은 기간 해당 종목을 단순 보유했다면 -47.95%였다.
알트 시장이 반토막 나는 구간에서 전략은 흑자였고, 시장에 노출된 시간은 3.9%뿐이다.

전략 함수가 아니라 **TradingEngine 전체**를 240분봉 200일 구간에 재생한 결과다.


## 몬테카를로 시뮬레이션 — 결론이 뒤집힌 지점

위 검정은 "실제로 일어난 과거 한 경로"에서의 결과다. 그 경로가 운이었을
가능성을 분리하려면 분포가 필요하다. `python -m ubbit simulate` 로 두 가지를
돌렸다.

| 시나리오 | 경로 | 중앙값 | 하위 5% | 상위 5% | 흑자확률 |
|---|---|---|---|---|---|
| 거래 순서 재표집 | 10,000 | **+22.62%** | -0.7% | +52.4% | 94.4% |
| **엔진 합성 경로** | **72** | **-0.59%** | -18.1% | +16.2% | **47.2%** |
| 단순보유 (같은 경로) | 72 | +2.81% | -21.2% | +57.2% | 55.6% |

**합성 경로에서 전략이 단순보유를 이긴 비율은 40.3%다.**

두 시뮬레이션이 갈리는 이유가 전부다. 거래 순서 재표집은 **실현된 거래 손익
분포를 그대로 유지**한 채 순서만 섞는다. 엣지를 전제에 넣고 시작하므로 좋게
나오는 것이 당연하다. 엔진 합성 경로는 가격 시계열을 새로 만들고 진입 판단부터
다시 돌린다. **엣지를 매번 새로 벌어야 한다.** 그러자 동전던지기가 됐다.

합성기 자체는 검증했다. 블록 크기를 시계열 전체 길이로 두면 원본 경로가
재현되고, 그때 전략 성과도 실제 백테스트와 일치한다(실제 평균 +0.32% vs
합성 -0.25%, 단순보유 -9.58% vs -9.63%). 시뮬레이터 버그가 아니다.

블록 크기 민감도도 확인했다. 추세추종 전략이라면 블록을 키워 장기 추세를
보존할수록 성과가 회복돼야 한다. 그러지 않았다.

| 블록 | 보존 기간 | 전략 중앙값 | 단순보유 중앙값 | 초과수익 |
|---|---|---|---|---|
| 5 | 20시간 | -0.39% | +10.42% | **-10.81%p** |
| 20 | 80시간 | -0.30% | +12.80% | **-13.10%p** |
| 60 | 240시간 | -0.36% | +8.22% | **-8.58%p** |
| 120 | 480시간 | -0.50% | +4.84% | **-5.35%p** |
| 240 | 960시간 | -0.37% | +4.20% | **-4.57%p** |

### 그래서 검정은 왜 통과했나

순열검정의 귀무가설은 "**같은 과거 가격 경로 위에서** 무작위 시점에 진입"이었다.
그 경로에 실제로 있었던 추세는 귀무세계에도 그대로 남아 있다. 즉 검정이 확인한
것은 "그 역사 안에서 진입 시점을 고르는 능력"이지 "어떤 시장에서도 통하는 규칙"이
아니었다. 가격을 새로 만들자 엣지가 사라졌다.

**정정한다. 이 전략은 수익성이 입증되지 않았다.** 검정 통과는 표본 하나에
대한 진술이었고, 더 강한 검정이 그것을 기각했다.

### 시뮬레이션의 한계

엔진 합성 경로는 72개뿐이다. 흑자확률 47.2%의 이항 표준오차가 약 5.9%p이므로
95% 구간은 대략 35~59%다. "확실히 진다"가 아니라 **"이긴다는 근거가 없다"**가
정확한 표현이다. 블록 부트스트랩은 블록 경계에서 장기 구조를 끊으므로
추세추종에 불리하게 작용할 수 있다. 다만 블록을 960시간까지 키워도 회복되지
않았으므로, 그것만으로는 설명되지 않는다.

### 원래 검정 결과를 어디까지 믿어야 하는가

**CI 하한이 +0.0056%다.** 0에 거의 붙어 있다. 기대값이 소수의 큰 수익에 의존한다는
뜻이고, 실제로 **거래당 순수익의 중앙값은 -1.86%**다. 손실은 자주·작게, 수익은
드물게·크게 나는 전형적인 추세추종 분포다. 표본이 조금만 달라져도 평균은 흔들린다.

**60분봉은 p-value가 0.0010으로 가장 강했지만 CI 하한 -0.0059%로 탈락했다.**
거래 639건, breadth 71%, 이익 집중도 7%로 다른 지표는 240분봉보다 낫다.
"진입 시점 선택에 정보가 있다"는 건 60분봉에서 더 분명하고, "기대값이 확실히
양수다"는 240분봉에서만 통과했다. 두 진술은 다른 것이다.

**15분봉은 명확히 음수다** (-0.0910%/거래, p=0.41). 단타 구간에서는 어떤 진입
방식도 무작위 진입과 구분되지 않았다. 수수료를 정직하게 반영하면 이 결론이 나온다.

**replay 결과는 추가 증거가 아니다.** 검증과 같은 데이터 구간을 쓴다. 엔진이
설계대로 동작하는지 보여주는 시연이다.

## 설치

```bash
git clone <repo> && cd ub-bit-API
pip install -r requirements.txt        # requests, PyYAML 둘뿐
cp config.example.yaml config.yaml     # 또는 config.scalp.yaml
```

API 키는 설정 파일이 아니라 환경변수로 넣는다.

```bash
export UPBIT_ACCESS_KEY=...
export UPBIT_SECRET_KEY=...
```

업비트 Open API 키 발급 시 **'자산조회' + '주문하기'만 체크하고 출금 권한은 절대 주지 말 것.**
허용 IP 등록은 선택이 아니라 필수다.

## 명령어

```bash
python -m ubbit costs                      # 비용 구조 분석 (키 불필요)
python -m ubbit scan                       # 종목×타임프레임 구조 적합성
python -m ubbit universe --unit 15         # 오늘 매매 자격 종목 선별
python -m ubbit fetch KRW-DOGE --unit 15 --count 5000
python -m ubbit backtest KRW-DOGE --unit 15 --trades
python -m ubbit validate --units 60 240 --modes breakout   # 엣지 통계 검증
python -m ubbit simulate --unit 240 --synthetic 60         # 몬테카를로 수익성 분포
python -m ubbit replay --unit 240          # 엔진 고속 재생 (주문 없음)
python -m ubbit optimize --markets KRW-DOGE --unit 60   # 워크포워드 재적합
python -m ubbit dashboard --db data/replay.db  # 브라우저 대시보드
python -m ubbit status --db data/replay.db # 포지션·누적 성과 (터미널)
python -m ubbit doctor                     # 키/권한/실측 슬리피지 점검
python -m ubbit paper                      # 가상매매 (실주문 없음)
python -m ubbit live --yes-i-know          # 실주문
```

### 5분 만에 돌려보기

```bash
pip install -r requirements.txt

python -m ubbit -c config.proven.yaml replay --unit 240 # 엔진 재생, 수 초
python -m ubbit -c config.proven.yaml dashboard --db data/replay.db
```

재생이 끝나면 실시간 페이퍼로 넘어간다. 터미널 두 개를 쓴다.

```bash
python -m ubbit -c config.proven.yaml paper          # 터미널 1: 봇
python -m ubbit -c config.proven.yaml dashboard      # 터미널 2: 화면
```

## 대시보드

`python -m ubbit dashboard` 로 띄운다. 표준 라이브러리 `http.server` 만 쓰고
외부 CDN 을 로드하지 않으므로 오프라인·사내망에서도 그대로 뜬다.
기본 바인딩은 `127.0.0.1` 이다. **잔고와 포지션이 노출되므로 외부에 열지 말 것.**

화면에 나오는 것:

- 총 자산, 현금/투입 비중, 고점 대비 낙폭
- **오늘 회전수와 그 확정 비용** — 회전이 늘수록 막대가 차오른다
- 자산 곡선 (인라인 SVG, 점선은 시작 자산)
- **비용 구조 패널** — 왕복 손익분기, 진입 변동성 하한, 일일 회전 비용
- 보유 포지션: 순손익(비용 차감 후), 손절까지 남은 거리, 목표 순익, 트레일링 활성 여부
- 최근 체결과 청산 사유 분포 (stop / take_profit / trail 비중)
- 누적 성과와 **통계적 판단 가능 여부** (거래 50건 기준)
- **긴급 정지 버튼** — 누르면 `.KILL` 파일을 만들어 신규 진입을 즉시 차단한다.
  보유 포지션의 손절·익절은 계속 동작한다.

`● 엔진 가동중` 표시는 최근 자산 기록 시각으로 판단한다. 봇이 죽으면
`N분간 갱신 없음` 으로 바뀐다. 대시보드는 DB 를 읽기만 하므로 봇과
별도로 띄우고 껐다 켜도 안전하다.

옵션: `--db <경로>` `--host` `--port`(기본 8777) `--no-browser`

권장 순서: `costs` → `scan` → `universe` → `fetch_all` → `validate` → `replay`
→ `doctor` → `paper`(8주+) → `live`(소액)

## 구조

```
ubbit/
  fees.py       비용 모델. 손익분기 배수, 체결 시뮬, 호가 기반 슬리피지 실측
  indicators.py EMA/RSI/ATR/Donchian (순수 파이썬, numpy 불필요)
  strategy.py   레짐 분류 + 수수료 인지형 진입/청산
  risk.py       사이징, 일일 손실한도, 회전수 상한, 쿨다운
  universe.py   매매 자격 종목 자동 선별
  session.py    업무 시간 세션 제어, 장마감 전량청산
  adapt.py      워크포워드 재적합 + 승격 게이트
  validate.py   부트스트랩 CI + 순열검정 + 베타 검증
  montecarlo.py 거래 재표집 + 합성 경로 몬테카를로
  replay.py     과거 캔들로 엔진 고속 재생
  dashboard.py  로컬 웹 대시보드 (표준 라이브러리만)
  reconcile.py  재기동 시 거래소 잔고 대조
  notify.py     웹훅 알림 (Slack/Discord)
  web/          대시보드 페이지
deploy/         systemd 유닛 + 감시 루프 스크립트
  broker.py     Paper / Live (동일 인터페이스)
  state.py      SQLite 영속화 (재기동 시 포지션 복원)
  engine.py     메인 루프
  backtest.py   백테스트 + 수수료 민감도
  upbit.py      REST 클라이언트 (JWT, rate limit, 재시도)
```

### 전략: 레짐 필터 + 비용 게이트 돌파

레짐은 네 가지로 분류한다. 이것이 "차트를 읽는다"의 재현 가능한 형태다.

- `dead` — ATR%가 손익분기×4 미만. **매매하지 않는다.** 이기더라도 수수료가 먹는다.
- `chaos` — ATR%가 상한 초과. 손절이 갭으로 건너뛴다. 매매하지 않는다.
- `bull_trend` / `bear_trend` / `range` — EMA 배열과 기울기로 판정.

진입은 `bull_trend`에서만, 아래를 **전부** 만족할 때:
직전 N봉 고가 돌파 / RSI 50~78(과열 꼭지 배제) / 거래대금 20봉 평균 대비 확장 /
그리고 **목표 순익이 손익분기를 넘길 것**.

청산은 하드손절(ATR×1.5), 트레일링(손익분기 돌파 후 활성), 목표 순익 도달,
레짐 이탈, 시간 손절 중 먼저 닿는 것.

### 리스크 게이트 (전부 하드 정지)

자동매매에서 계좌를 죽이는 건 잘못된 신호가 아니라 사이즈와 정지 규칙의 부재다.

- 손절폭 역산 사이징 — 변동성이 달라도 1회 손실은 자본의 0.4~0.5%로 고정
- 일일 손실한도 도달 시 당일 매매 중단
- 일일 매매 횟수 상한 — 설정 검증 단계에서 **회전수의 확정 비용 드래그가
  일일 손실한도를 넘으면 실행을 거부**한다
- 연속 손절 시 쿨다운, 종목별 재진입 쿨다운
- 킬스위치: `.KILL` 파일 생성 → 신규 진입 즉시 차단(청산은 계속 동작)

### 세션 제어

기본값 평일 09:00~18:00 KST, 종료 20분 전 신규 진입 중단, **장 마감 전량 청산**.

마감 청산은 손실 중이어도 실행한다. 단타 손절폭은 봉 단위로 설계되는데
밤사이 급락은 그 손절폭을 통째로 건너뛴다. 설계된 손실 한도가 지켜지지 않는다.
`session.enabled: false`로 24시간 운용할 수 있지만, 새벽 시간대는 호가가 얇아
같은 신호에서도 슬리피지가 커진다.

### 파라미터 재적합

시장은 변하므로 재적합은 필요하다. 그러나 재적합은 자동매매에서 가장 비싼 실패
경로이기도 하다. 그래서 `adapt.py`는 최적화기가 아니라 **승격 심사기**다.

- 실행 루프(수십 초)에서 규칙은 **절대 스스로 바뀌지 않는다.** 재적합은 별도
  프로세스가 파일에 쓰고, 엔진은 그 파일을 읽기만 한다.
- 학습 구간에서 고른 파라미터는 **미사용 구간(OOS)에서 재평가**하고, 보고하는
  성과는 OOS 성과다.
- 탐색 그리드는 4축 81조합으로 **의도적으로 작게** 유지한다.
- 최적화 대상은 전략 파라미터뿐이다. **비용 모델과 리스크 게이트는 대상이 아니다.**
  파라미터 파일이 손상·조작되어도 `min_net_target` 같은 안전 하한은 무력화되지 않는다
  (화이트리스트 방식).
- 승격 조건: OOS 거래 30건 이상 / OOS 수익률 양수 / 챔피언 대비 +1%p 이상 /
  MDD 15% 이내 / 수익 폴드 비율 60% 이상. **하나라도 미달이면 거부가 기본값이다.**

실제로 DOGE·NEAR 15분봉 12폴드 재적합을 돌린 결과 두 건 모두 승격 거부됐다
(표본 부족 17·24건, 수익 폴드 비율 25%·50%). 의도한 동작이다.

## 한계 — 이 봇이 못 하는 것

**백테스트가 재현하지 못하는 것**: 호가 소진(대형 주문의 실제 슬리피지), 거래소
장애·지연, 본인의 개입. 백테스트 수치는 상한선이며 실거래 기대치는 그보다 낮다.

**페이퍼가 재현하지 못하는 것**: 위와 동일. 페이퍼 흑자가 실거래 흑자를 보장하지 않는다.

**LLM이 차트 이미지를 보고 매매 판단을 내리는 구조는 채택하지 않았다.**
응답 지연이 수 초 단위라 15분봉 종가 진입에도 슬리피지가 붙고, 같은 차트에 같은
답이 나온다는 보장이 없어 성과 귀인이 불가능하며, 호출 비용이 회전당 손익과
같은 자릿수다. 외부 신호를 붙이고 싶다면 진입을 **추가하는** 방향이 아니라
**거부하는**(veto) 방향으로만 연결할 것.

**세금**: 국내 가상자산 소득 과세는 2027년 1월 시행 예정이다. 시행 시점과 세부
기준은 변동 가능하므로 실제 세후 수익률은 별도 확인이 필요하다.

## 무인 운용

키를 넣고 `live` 를 띄우면 사람 개입 없이 돈다. 다만 **프로세스가 죽으면
손절 주문이 나가지 않는다.** 자동매매의 실제 손실은 전략 오류보다
프로세스 중단에서 더 자주 나온다. 반드시 감시 하에 띄운다.

```bash
# Linux (systemd)
sudo cp deploy/ubbit.service /etc/systemd/system/
sudo cp deploy/ubbit.env.example /etc/ubbit.env   # 키 입력 후 chmod 600
sudo systemctl enable --now ubbit
journalctl -u ubbit -f

# macOS / WSL
./deploy/run.sh config.proven.yaml
```

둘 다 죽으면 15초 후 재시작하고, **10분 안에 5회 넘게 죽으면 멈춘다.**
무한 재시작은 같은 실패 주문을 반복해 상황을 악화시킨다.

### 재기동 잔고 대조

기동할 때마다 로컬 DB 와 거래소 실제 잔고를 대조한다 (`reconcile_on_start`).

- **DB 에 있는데 계좌에 없음** → 관리 중단. 그대로 두면 손절이 매 주기
  실패하는데 봇은 지키는 중이라 착각한다. 손익은 추정하지 않고 0 으로
  기록하므로 실제 손익은 업비트 거래내역에서 확인해야 한다.
- **부분만 남음** → 실제 수량으로 축소하고 계속 관리한다.
- **계좌에 있는데 DB 에 없음** → 경고만 한다. **절대 자동으로 팔지 않는다.**
  사용자의 장기 보유분일 수 있기 때문이다. 직접 처리하거나 계좌를 분리한다.

`engine.halt_on_mismatch: true` 로 두면 불일치 시 아예 기동하지 않는다.
사실과 다른 상태를 믿고 도는 것보다 안 도는 편이 안전하다는 판단이면 켠다.

### 알림

봇이 조용히 망가지는 것을 막으려면 웹훅을 건다. Slack Incoming Webhook 과
Discord Webhook 을 모두 지원한다.

```bash
export UBBIT_WEBHOOK_URL=https://hooks.slack.com/services/...
```

전송 대상은 진입, 청산, 매매 중단(손실한도·쿨다운), 주문 실패,
재기동 잔고 불일치, 엔진 시작·정지다. 체결 하나하나를 다 보내지는 않는다.
알림이 잦으면 정작 중요한 것을 놓친다. 알림 전송이 실패해도 매매는 계속된다.

이 코드는 실제 자금을 움직인다. 손실 책임은 전적으로 운용자에게 있다.

**현재 이 저장소의 어떤 전략도 수익성이 입증되지 않았다.** breakout @ 240분봉은
순열검정을 통과했으나, 가격 시계열을 새로 생성한 몬테카를로에서 흑자확률

코드는 재사용 가치가 있다. 비용 모델, 리스크 게이트, 검정 도구, 대시보드는
다른 전략을 검증하는 데 그대로 쓸 수 있다. 검증되지 않은 것은 전략이지
인프라가 아니다.
